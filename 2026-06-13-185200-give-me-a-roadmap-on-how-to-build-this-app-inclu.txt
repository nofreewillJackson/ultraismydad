  from the directory name. Here's the order I looked, and why:

  assuming.
  2. I let the file tree tell me the shape. docs/ had four big markdown files
  and a dev-log/; src/ had only two tiny domain files. That mismatch is the
  whole story: this is a documentation-first, clean-room rebuild that has barely
  started. The spec exists; the code doesn't yet.
  3. I read the docs in dependency order, not alphabetical. DOMAIN_PRIMER (the
  what), TECH_STACK (the physical facts), BEHAVIOR_INVENTORY (the testable 
  checklist), then CLEANROOM_SPEC (the architecture + what to keep vs delete). I
  read the spec last on purpose — it's the synthesis, and it only makes sense
  once you've seen the raw rules it's reacting to.
  4. I read the dev-log to find the current frontier. It told me exactly three
  TDD cycles are done and why each decision was made. That's where the roadmap
  has to continue from.
  5. I loaded the methodology the project actually uses (the TDD playbook)
  instead of applying generic "best practices." The roadmap has to obey this
  project's rules, not my defaults.

  ▎ The meta-skill: a roadmap is not invented, it's derived. You read the 
  ▎ source-of-truth docs, find the current frontier, and let the project's own 
  ▎ stated principles dictate the ordering. Most of my "decisions" below are me 
  ▎ applying rules the docs already state — the skill is knowing which rule 
  ▎ applies where.

  ---
  Part 1 — The one decision that shapes the entire roadmap

  The CLEANROOM_SPEC hands you a single test (§0.5) and it governs everything:

  ▎ Would this survive if the author had picked a different stack on day one?
  ▎ Yes → it's domain, build it. No → it's an accident, delete it (don't 
  ▎ lovingly re-implement it).

  This is the most important thing for a junior to internalize: a rebuild is not
  a port. The legacy app is ~80% machinery (snapshot exporter, dirty-flag
  ledger, five-deep fallback cascade, keyword-inference cascades, per-record
  patch maps). The spec's whole argument is that almost none of that is domain.

  What survives the test (this is what you actually build):
  - The privacy boundary — default-deny, enforced once. This is the spine of the
  whole app.
  - Explicit relationships — product line is a required FK captured at authoring
  time, not guessed at read time.
  - Path-free public contracts — the read snapshot (Contract A) and the video
  bundle (Contract B).
  - Derived presentation — slugs, timeline/day math, heatmap, counts, sort
  order, embeddability. Pure functions.
  - The media-ingestion ETL as a content-prep concern.

  What you delete (do NOT port):
  - The bake / snapshot-exporter / dirty-flag / publish-ledger apparatus as 
  architecture (§3.4).
  - Every inference cascade (line, series, video↔item title-matching).
  - The catch-all product line, the dual stack lists, name aliases, the gated
  state, snapshotHtml.
  - Per-record override maps hardcoded in code; the foreign absolute backup
  path; the three slugify copies.

  ▎ How I inferred the roadmap's spine from this: if the privacy gate is the one
  ▎ non-negotiable domain invariant, then it must be the first thing proven and
  ▎ the thing every later phase routes through. The TDD playbook independently 
  ▎ agrees (§10: trust-boundary tests come before happy-path). Two sources 
  ▎ pointing at the same starting point = high confidence.

  ---
  Part 2 — The fixed frame vs. what emerges

  The playbook's prime rule: macro-architecture is fixed, micro-design emerges.

  Fixed (you don't get to TDD your way out of these):
  - Clean Architecture dependency direction: domain → nothing, use-cases → 
  domain, adapters/UI → use-cases. Business rules never live in routes,
  components, ORM models, or scripts.
  - Vertical slices: prove the thinnest meaningful end-to-end path early, so you
  don't build "glass invariants" — rules that look right in memory but shatter
  against real persistence.
  - Owned infrastructure (your store, your filesystem) gets tested against real 
  ephemeral infra; only third-party services get faked.

  Emerges (one failing test at a time): every function signature, every
  interface, every file split. You do not pre-plan the class diagram.

  ▎ Why this matters for the roadmap: it tells me what the phases can't be. I 
  ▎ can't have a "build all the domain entities" phase followed by "build all 
  ▎ adapters" — that violates vertical slicing. Each phase has to be a slice 
  ▎ that's provable and useful on its own.

  ---
  Part 3 — The phased roadmap

  Each phase below states the goal, why it's here and now (the inference), and
  the first behaviors to TDD. Phases are ordered by risk reduction and
  dependency, which is how you should always order a build: do the thing that,
  if wrong, invalidates the most other work.

  Phase 1 — Pure domain core (in progress)

  Goal: the entities and invariants as pure, in-memory functions. No I/O, no
  framework.
  Status: 3 cycles done — createWorkItem (defaults visibility→private,
  line→catch-all) and selectPublicWorkItems.

  Why first: it's the innermost layer; everything depends on it and it depends
  on nothing, so it's the cheapest to get right and the most expensive to get
  wrong. The privacy gate (selectPublicWorkItems) is already the trust boundary
  — correct instinct.

  Behaviors still to TDD here (pull straight from BEHAVIOR_INVENTORY §A, §N):
  - Visibility rules for every collection — and unify them to default-deny (spec
  §3.1 #8). Legacy used =="public" for items but !="private" for
  lines/series/tech; the spec says pick one. Decision: explicit public/private, 
  default-deny, everywhere.
  - Slug derivation: lowercase → collapse non-alphanumerics → trim → cap at 80;
  log-slug collision de-dup with a short id suffix. (One slugifier — legacy had
  three that disagreed.)
  - Timeline math: dayNum, shipped count, active-days; campaign counter only
  when a campaign config supplies a target (the "100" is presentation, not a
  domain limit — §0.5).
  - Embeddability: host allow-list AND not-deny-list; inline demo HTML beats
  external link.
  - Sort order, technology rollups (resolve refs → count → group by category).

  ▎ ⚠️ A correction I'd flag before continuing Phase 1. Cycle 2 defaulted 
  ▎ productLineId to a catch-all constant. But CLEANROOM_SPEC §1.3 and §2.4 #7 
  ▎ explicitly say catch-all is an accident — do not port; product line should 
  ▎ be a required FK. The dev-log's reasoning ("keep authoring frictionless") is
  ▎ reasonable, but it contradicts the source of truth. This is the single most
  ▎ important teaching moment in the whole project: your own earlier code is 
  ▎ not exempt from the domain-vs-accident test. The spec's intent is that the 
  ▎ editor makes line selection mandatory (with inference offered as a one-time 
  ▎ suggestion, never a runtime fallback), so there are no unresolved items and 
  ▎ no catch-all sink. I'd revisit this with you (see Decisions below) before 
  ▎ building more on top of it.

  Phase 2 — First vertical slice: derisk the whole architecture

  Goal: one behavior, end to end: persist a public work item → run it through 
  the export gate → render its detail page.
  Why now, before broadening the domain: the playbook warns against glass
  invariants. Phase 1 rules look correct in memory; this slice proves they
  survive contact with real persistence and a real renderer. It forces you to
  define — minimally — a store port, one real ephemeral adapter (e.g., temp
  SQLite or a temp-dir filesystem store), the export use case, and one render 
  path. If the architecture is wrong, you find out now with one feature, not
  after twenty.
  Inference source: playbook §3 (vertical slice rule) directly.

  Phase 3 — The read-model contract (Contract A) + the single export gate

  Goal: one use case that takes the full operational dataset and emits the
  sanitized read snapshot: privacy filter applied once, timestamps normalized,
  arrays guaranteed, slugs deduped, non-public records absent entirely.
  Why here: this is the testable embodiment of the one domain invariant. Spec
  §3.3 #3: "a test that asserts no non-public record ever appears downstream."
  Everything the delivery side reads comes from this contract, so it must exist
  before you build readers.
  Key behaviors: the §N trust-boundary checklist — private/gated/unset items
  excluded; private logs hidden; the integrity validator that fails the build
  when a public item's tech ref doesn't resolve or uses the forbidden other
  placeholder.

  Phase 4 — Delivery / rendering (the public read side)

  Goal: the pre-rendered pages and feeds: home/graph, list, map, project, video,
  log, research, plus rss.xml, llms.txt, robots.txt, sitemap, 404, and the
  legacy redirects.
  Why after Contract A: readers are pure consumers of the snapshot; they can't
  be built before the contract they read. Test the logic, not the pixels
  (playbook §12): log author-filter + empty states, embeddability rendering
  decision, files-tab visibility, three-state file gating. Visual layout is
  manual/snapshot verification.
  Inference: BEHAVIOR_INVENTORY §G–K are this phase, almost line for line.

  Phase 5 — Authoring surface + identity gate

  Goal: the admin: Google SSO → allow-list authz (authenticated ≠ authorized; a
  non-operator is force-signed-out), CRUD over items/lines/series/taxonomy, new 
  items default private, explicit line/series/tech selection (the FK capture
  that replaces inference).
  Why this late: it's heavy on trust boundaries (do those first within the
  phase, §10), and it depends on the store and domain being solid. It's also
  where you delete inference by making relationships explicit at the point of
  capture — which only makes sense once the read side proves what the
  relationships are for.

  Phase 6 — Media ingestion ETL (Contract B)

  Goal: turn production artifacts into clean, path-free video bundles + index.
  Why near-last and standalone: the spec calls it "conceptually separate" — it's
  a parallel pipeline, not on the critical path of the main publish flow, so it
  doesn't block anything else. Redesign, don't port: legacy parses human-edited
  prose with regex (§3.1 #6); the rebuild makes the authored source structured
  so ingestion is a parse, not a guess.

  Phase 7 — The digital garden

  Goal: file-based notes, wikilink resolution, backlinks, bounded transclusion,
  and the graph analytics (communities, hubs, orphans, latent links).
  Why it can float: it's self-contained (file-based, not in the store, its own
  renderer). It has no dependency on Contract A, so it can be built any time
  after Phase 1 — even in parallel by another person. I place it late only
  because it's the most isolated and lowest-risk.

  ▎ The cross-cutting decision baked into every phase: store relationships, 
  ▎ derive presentation (spec §3.3 #1). When a phase needs a relationship (line,
  ▎ series, video↔item) → it's a stored FK. When it needs a number or a label 
  ▎ (day count, heatmap, slug, sort) → it's a derived pure function. This one 
  ▎ rule resolves most "where does this go?" questions before you even ask them.

  ---
  Part 4 — How to choose the next test inside any phase

  The roadmap gives you phases; the playbook gives you the within-phase loop.
  For a junior, this is the actual day-to-day skill:

  1. Trust boundaries before happy paths. If the behavior touches
  privacy/auth/integrity, its rejection test comes first (§10).
  2. Pick the simplest unproven behavior off the BEHAVIOR_INVENTORY checklist —
  that file is literally a pre-made behavior inventory, one checkbox = one TDD
  cycle.
  3. RED → GREEN → REFACTOR, and actually run it. Write one failing test,
  observe it fail for the right reason (missing behavior, not a typo), write the
  minimum to pass, then refactor under green. Never write test + impl in one
  step.
  4. New edge cases get added to the list, not implemented on the spot.

  ▎ Why I'm handing you the heuristic instead of a 200-line task list: the 
  ▎ playbook's core claim is "micro-design emerges." A roadmap that 
  ▎ pre-specified every test would itself violate the method you're learning. 
  ▎ The phases are the fixed frame; the tests emerge.

  Why the spec is overzealous about the bake

  The CLEANROOM_SPEC runs every mechanism through one test (§0.5): "would this 
  survive a different day-one stack? No → accident." Applied to the bake, it
  concludes "a cached server dissolves it, therefore accident."

  The flaw: that test proves too much. Firestore wouldn't survive a different
  stack. TypeScript wouldn't. The test is meant to separate domain from
  implementation — but "bake vs. server" isn't domain-vs-implementation, it's a
  choice between two delivery tactics, and the spec itself concedes this in §3.3
  #6: "How you achieve cheap reads (static bake, incremental regeneration, edge
  cache) is a stack choice. Preserve the property, not the machine." So the
  spec simultaneously calls baking a valid tactic and an accident-to-delete.
  That contradiction is the tell.

  What the spec misses is that, for this specific domain, baking is not neutral
  — it's arguably the stronger tactic, because of what the domain says matters
  most:

  - The spec's own #1 non-negotiable invariant is a hard privacy boundary. A
  bake with an export-time filter makes non-public data physically absent from
  the delivery artifact — there is no request-time code path that could leak it,
  because there's no live store on the read path at all. The spec's proposed
  alternative moves that gate to a runtime query filter, which is strictly
  weaker: one missed WHERE visibility='public' and you leak the thing the domain
  cares about most.
  - Pre-publish integrity gate. build:strict refuses to ship when the taxonomy
  doesn't resolve. A live server renders the broken record to a real visitor.
  Baking moves failure left.
  - Atomic, immutable, rollback-able releases and zero runtime surface (no
  server, no DB creds on the read path) — durable properties, not accidents.

  The steelman for the spec's side is incremental regeneration (ISR): "automatic
  freshness, no exporter." But ISR still runs render code against the live
  store on revalidation — the read path does touch the write store, just less
  often — and it buys freshness latency, a metric a personal archive that
  publishes a few times a week barely cares about, at the cost of the physical
  privacy + atomic-rollback + pre-publish-validation properties it cares about a
  lot.

  So: the spec conflated two different things. The bake (delivery tactic) is
  sound — keep it. The cruft around it — the manual trigger, the five-deep
  fallback cascade with a hardcoded foreign absolute path, the unwired
  dirty-flag — those are the real accidents. Fix those, keep the bake, and make
  the trigger event-driven. The user's instinct is the correct refinement.

  Now let me write the roadmap with that position in it.
